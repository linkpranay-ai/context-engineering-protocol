## 2. Task

Write functional user stories for ripgrep's `--trim`/`--no-trim` flag: a
real, shipped flag (introduced by issue #917) that strips leading ASCII
whitespace from each printed matching line, plus its execution-order
relationship with `-M`/`--max-columns` truncation (trim must run first —
a real ordering bug fixed by PR #2458). Phrased as a developer would
actually hand it to a user-story-writing tool:

> "Add a `--trim`/`--no-trim` flag to ripgrep that strips leading ASCII
> whitespace from each printed matching line, and make sure trimming
> happens before `-M`/`--max-columns` truncation is applied."

This flag was chosen deliberately over re-using the CRLF/`--replace`
feature the earlier case study already covered: it's a different, equally
real and equally traceable subsystem (a distinct flag, a distinct GitHub
issue and PR), so this case adds a second, independent data point rather
than re-measuring the same code paths.

## 9. Limitations

- **Single feature, single run.** One flag, one case. Do not extrapolate
  to "CEP always finds N extra stories" from this alone.
- **Same agent authored both modes.** Unlike a blind A/B test, the agent
  that generated the context package also wrote the Mode 2 "bare ask"
  output in the same session, with the same underlying knowledge
  available to it. Mode 2 was deliberately constrained to only the literal
  words in the feature description, but this is an authoring discipline,
  not a structural guarantee the way two independently-blinded runs would
  be.
- **The "0 hallucinations" cell is not the headline finding here, and
  that's itself worth disclosing.** The two prior consumer-benefit cases
  in this repo (`consumer-benefit-user-stories`,
  `open5gs-gy-supported-features`) both found the bare-ask baseline
  fabricated a plausible-sounding API or concept. This run didn't. The
  likely reason: this feature description is already technically precise
  (it names the exact flags, `--trim`/`--no-trim`/`-M`/`--max-columns`),
  leaving little surface for a bare ask to invent specifics on. A vaguer
  ask ("clean up ripgrep's output formatting") would likely have more
  hallucination surface. So the hallucination-suppression benefit measured
  in prior cases should be read as conditional on how underspecified the
  input request is, not as a universal guarantee CEP provides regardless
  of input.
- **Dogfooding self-approval, no live human reviewer** — disclosed per
  standing convention, same as every other case in this repo.
- **New, unpolished skill.** `demo-write-user-stories` is a lean,
  from-scratch reference implementation built for this case study, not a
  battle-tested production tool — its actor-identification and
  story-writing steps are plain heuristics, not a validated methodology.

## 10. Lessons learned

- The generative-benefit finding from the two prior consumer-benefit cases
  (more specific actors, more grounded, non-inventable claims per story)
  reproduces a third time here — on an unrelated language/ecosystem (a
  Rust CLI tool, not a Python UI framework or a telecom protocol stack)
  and using a brand-new, independently-designed consuming skill built
  without reference to either prior skill's internals. That's evidence the
  pattern is about the *context package*, not about one particular
  skill's prompt engineering.
- Hallucination suppression specifically should not be marketed as
  unconditional — see §9. It's real when the input is underspecified, and
  this case shows it isn't the only lever CEP pulls: actor specificity and
  coverage of unknowable-without-grounding facts (existing test coverage,
  a subtle edge-case interaction) held up even when the fabrication axis
  didn't move.
- The `graphify affected` low-degree-leaf limitation (first found in
  `ripgrep-crlf-replace-terminator`) recurred on a second, unrelated
  feature in the same codebase. Worth treating as a real, repeatable
  pattern of the tool (not a one-off) in the governance-side defect log
  already tracking it, rather than a coincidence specific to the CRLF
  case's particular node.
